### 검증할 가설

설계 1장은 "'왜'를 진단하는 도구는 승자가 없다"는 빈틈을 가설로 두었다. 작은 도구들이 자리를 잡지 못한 까닭이 아직 승자가 없어서인지, 수요가 약해서인지는 공개 뒤의 반응으로만 알 수 있다. 3-2는 다음을 본다.

- **H1 수요:** 이 진단 방식에 관심을 보이고 직접 써 보는 사람이 있는가.
- **H2 방향:** 원인 분해가 사용자의 감각과 맞는가. 큰 세션 정리 안내가 쓸모 있는가(소개 글이 직접 묻는 두 가지).
- **H3 환경:** 확인하지 못한 환경(Intel, macOS 14 ~ 26, 터미널 위주 사용자, 5분 캐시, 200K 컨텍스트)에서 동작과 분류가 맞는가.

**실질 피드백의 정의:** 오너와 AI가 아닌 사람이 앱을 설치하거나 써 본 뒤 남긴 이슈, PR, HN·GeekNews 댓글이다. 같은 사람이 여러 번 쓰면 1건으로 센다. 써 보지 않은 일반 의견("좋은 생각이다", "이미 X가 있다")은 세지 않고 따로 적는다. 피드백마다 방향을 하나 붙인다.

| 방향 | 예 |
|---|---|
| 맞음 | 원인 분해가 생각하던 것과 맞다, 정리 프롬프트가 도움이 됐다 |
| 틀림 | 수치나 분류가 틀렸다, 숫자가 이상하다 |
| 환경 | 설치, 실행, 권한 문제(Intel, macOS 14 ~ 26 보고 포함) |
| 이미 있음 | 다른 도구로 충분하다 |
| 다른 것을 원함 | 한도 %, 다른 도구 지원, Windows·Linux 같은 비목표 |
| 신뢰 | 개인정보나 보안에 대한 우려 |

**내려받기 해석:** 새로 설치하는 사람은 그때의 최신 버전 zip을 받는다. 관찰 중에 새 버전을 내면 기존 사용자의 업그레이드가 새 자산에 더해지므로, 릴리스 직전의 이전 버전 증가분을 그때까지의 설치 수 상한으로 적고, 새 버전의 증가분에는 업그레이드가 섞였다고 표시한다. 릴리스마다 오너와 AI, 워크플로의 검증용 내려받기 수를 진행 기록에 적어 뺀다.

### 기준선 규칙과 관찰 일정

- **0점(D+0):** 첫 소개 글(Show HN이나 GeekNews 중 먼저 올리는 것)을 올리기 직전의 마지막 스냅숏이다. 오너가 "곧 올린다"고 알리면 AI가 스냅숏을 찍고, 오너가 올린다. 알림 없이 올렸다면 게시 시각 이전의 마지막 스냅숏을 쓰고, 별은 `stargazers/history`로 게시 시각에 맞춰 다시 센다.
- **게시 기록:** 오너가 두 글의 링크와 게시 시각(UTC)을 알려 주면 관찰 기록에 적는다. 두 글 사이의 반응은 리퍼러(`news.ycombinator.com`, `news.hada.io`)로 나눈다.
- **관찰 기간:** D+0부터 30일. 소개 글의 반응은 처음 며칠에 몰리고, 30일이면 저장소가 만든 지 30일이 되는 공식 cask 조건 시점(2026-12-17)도 지난다.
- **스냅숏 시점:** D+0, D+1, D+7, D+14, D+30. 두 스냅숏의 간격이 14일을 넘으면 그 사이의 트래픽이 사라지므로, 일정이 밀려도 간격은 14일 이하로 지킨다.
- **누가 돌리는가:** 오너가 게시 직전과 각 시점에 중재자나 작업 세션에 알리면 AI가 돌린다(추천). 이 기기에 예약 작업을 만드는 방법도 있지만, 지속되는 설정이 생기고 Claude 사용량을 조금 쓰므로 오너가 고를 때만 만든다(게이트 4).
- **기록 위치:** `03-operations/reaction-check/observations.md`(계획 승인 뒤 다음 PR에서 만든다). 스냅숏 표, 게시 링크, 피드백 목록(이슈 번호나 글 링크, 방향, 한 줄 요약)을 둔다.

**스냅숏 명령** (`R=bingoring/tokens-are-running-out`, 오너의 `gh` 인증으로 실행):

```sh
date -u +%Y-%m-%dT%H:%MZ
gh api repos/$R --jq '{stars: .stargazers_count, forks: .forks_count, watchers: .subscribers_count}'
gh api repos/$R/releases --jq '.[] | [.tag_name, (.assets[] | select(.name | endswith(".zip")) | .download_count)] | @tsv'
gh api repos/$R/traffic/views --jq '{count, uniques}'
gh api repos/$R/traffic/views --jq '.views[] | [.timestamp[0:10], .count, .uniques] | @tsv'
gh api repos/$R/traffic/popular/referrers --jq '.[] | [.referrer, .count, .uniques] | @tsv'
gh api repos/$R/traffic/clones --jq '{count, uniques}'
gh api repos/$R/stargazers/history
gh issue list -R $R --state all --limit 100 --json number,title,createdAt,labels
curl -s https://hacker-news.firebaseio.com/v0/item/<HN 글 번호>.json | jq '{score, descendants}'
```

GeekNews는 API를 확인하지 못했으므로 글 화면에서 점수와 댓글 수를 읽는다.

### 판정 기준 (데이터를 보기 전에 고정한다)

기준점은 이미 가진 숫자에서 가져왔다. **27**은 같은 문제를 노린 도구 가운데 가장 큰 것의 별 수다(설계 1장, 2026-11-17 GitHub 검색, 2차 자료). **75**는 공식 `homebrew/cask`에 다른 사람이 제출할 수 있는 인지도 기준이다(3-1 외부 사실 표, 공식 확인).

**1단계, 노출(D+14):** 게시 뒤 14일의 고유 방문자가 300 이상이면 "노출 충분"이다. 300 미만이면 별이 0이어도 수요에 대해 말해 주는 것이 없으므로 **판정 불가(노출 부족)** 로 둔다. 300은 근거가 약한 제안값이다. 방문자 300명이 보고도 별과 피드백이 없다면 관심이 매우 낮다고 말할 수 있는 정도의 수다.

**2단계, 반응(D+30, 노출 충분일 때):**

| 판정 | 조건 | 다음 행동 |
|---|---|---|
| **지지** | 별 75 이상, 또는 실질 피드백 5건 이상 | 후속 후보를 잠정 순위대로 다음 Construction 스테이지로 제안한다. 공식 cask 조건(별 225와 30일, 또는 다른 사람의 제출)을 다시 본다 |
| **불충분** | 별 28 ~ 74, 또는 실질 피드백 2 ~ 4건 | 피드백에 나온 결함 수정과 작은 개선만 한다. 큰 기능(일반 작업 분해, 세션 내용 체크리스트)은 다음 판정까지 미룬다 |
| **기각** | 별 27 이하이고 실질 피드백 0 ~ 1건 | 유지보수만 한다(결함 수정, 기록 형식 변화 대응). 설계 1장의 가설을 "이 채널에서 확인되지 않음"으로 기록한다 |
| **판정 불가** | 노출 부족 | 다른 채널에 소개할지 오너가 정한다. 소개하면 같은 기준으로 관찰을 다시 시작한다 |

- 두 조건 가운데 높은 쪽으로 판정한다. 피드백이 주 신호이므로, 별이 적어도 피드백이 있으면 그쪽을 따른다.
- **방향 판정:** 실질 피드백 중 "틀림"이 1건이라도 있으면 판정과 관계없이 그 확인을 먼저 한다. "이미 있음"이나 "다른 것을 원함"이 "맞음"보다 많으면, 판정 옆에 "수요의 형태가 다르다"를 함께 적고 후속 순위를 다시 본다.
- 공식 cask: 소유자가 직접 제출하려면 별 225(또는 포크·watcher 90)와 저장소 나이 30일(2026-12-17부터)이 필요하다. 기준을 넘어도 등록이 보장되지는 않으므로, 넘으면 그때 별도 스테이지로 제안한다.

### 기본값 재판단

앱은 네트워크로 아무것도 보내지 않으므로(반목표 3), 다른 사용자의 수치는 사용자가 직접 올린 보고로만 얻는다. 3-2에서는 기본값을 바꾸지 않고, 바꿀 근거가 있으면 후속 Construction 스테이지를 제안한다.

**받는 곳:** 「결과 공유(Share your numbers)」 이슈 템플릿을 게시 전에 넣는다(게이트 5). 기존 버그 보고 템플릿처럼 대화 내용, 세션 제목, 프로젝트 경로를 붙이지 말라고 먼저 안내하고, 다음만 묻는다.
- 앱 버전, macOS 버전, 칩
- 주로 쓰는 곳(터미널, 데스크톱 앱, IDE)과 모델, 컨텍스트 창(1M, 200K, 모름)
- 팝오버의 최근 7일 원인별 비율
- 메뉴 막대 숫자: 재구축 임계값 5만(기본)일 때와 1만일 때
- 큰 세션 영역에 세션이 나타난 적이 있는지, 정리 프롬프트를 써 봤다면 결과
- 원인 분해가 생각하던 것과 맞았는지(자유 기술)

소개 글 초안은 3-1 문서이므로 고치지 않는다. 오너가 게시할 때 마지막 문단에 "결과 공유 템플릿으로 수치를 알려 주면 기본값을 정하는 데 쓴다"는 한 문장을 더할지는 오너가 정한다.

**규칙:**
- **재구축 임계값 5만:** 수치를 담은 보고가 3건 미만이면 유지한다. 3건 이상이고 그 과반에서 1만과 5만의 메뉴 막대 숫자가 1%p 이상 다르면, 기본값을 낮추는 후속 스테이지를 제안한다. 개발자 기기에서는 1만 ~ 5만의 결과가 같았다(DECISIONS 2026-11-18). 다르다면 시작 컨텍스트가 작은 사용자에게서 5만이 재구축을 놓치고 있다는 뜻이다. 재구축 판정의 두 번째 조건(캐시 쓰기 > 캐시 읽기)이 있어 임계값을 낮춰도 잘못 잡는 경우는 적다.
- **큰 세션 기준 20만:** 보고가 3건 미만이면 유지한다. 200K 창 사용자에게 큰 세션 영역이 나타나지 않는 것은, 그들의 세션이 200K 경계에서 이미 자동 compact되어 큰 컨텍스트를 되읽는 비용이 1M 세션보다 작으므로, 결함이 아니라 맞는 동작으로 본다. 1M 창 사용자에게서 "늘 비어 있다"나 "늘 가득하다"는 보고가 2건 이상이면, 기준 변경이나 설정화를 후속 스테이지로 제안한다.
- **비교 기준:** 판정 시점에 개발자 기기의 최근 7일 기록으로 1만과 5만의 차이, 20만 이상인 실행 세션의 비율을 다시 계산해 보고와 나란히 둔다. 로컬 분석이며 집계만 적는다.

### 후속 후보와 잠정 순위

여러 문서에 흩어진 후보를 모았다. 순위는 잠정이며, 아래 재정렬 규칙에 따라 판정 뒤에 다시 정한다.

**재정렬 규칙:**
1. 정확도와 신뢰 문제("틀림", "환경", "신뢰" 피드백)는 판정이나 건수와 관계없이 먼저 한다.
2. 같은 요청이 실질 피드백 2건 이상에서 나오면 그 항목을 한 단계 올린다.
3. "기각"이면 P1만 하고 나머지는 보류한다. "불충분"이면 P1과 P2 중 피드백이 가리키는 것만 한다.

**P1, 반응과 관계없이 할 것(신뢰, 작은 결함):**
- 보고된 설치·실행 결함(Intel, macOS 14 ~ 26). 보고가 오면 바로 한다.
- 2-5 브랜치 리뷰의 사소한 항목 중 사용자 눈에 보이는 것: 제목 없는 세션의 한국어 접근성 이름("제목 없는 세션 세션의…"), 2초 안에 다시 누른 복사가 실패하면 "복사됨"이 남는 것, 클립보드 쓰기가 실패해도 기존 내용이 지워지는 것
- 3-1 `v0.1.1` 리뷰의 LOW: `register()`가 실패하면 토글이 안내 없이 꺼짐으로 돌아가는 것

**P2, 지지·불충분 판정에서 피드백이 가리킬 때:**
- **집계 복사:** 원인 분해와 재구축 목록을 세션 제목 없이 집계로 클립보드에 복사한다. 설계의 v2 후보 "버그 증거 내보내기"를 줄인 형태로, "틀림" 보고를 검증하고 결과 공유 보고를 쉽게 만든다. "틀림" 보고가 1건이라도 오면 P2의 첫째가 된다.
- **일반 작업 비용 분해와 advisor 표시(2-5 제외):** 가장 큰 항목(최근 7일 47%)의 속이 보이지 않는다는 문제다. "일반 작업이 무엇인지 모르겠다"는 피드백이 오면 올린다.
- **compact 호출 비용 추정(DECISIONS 2026-11-23):** 자동 compact의 비용이 원인 분해에서 빠진다. 정확도 문제다.
- **메뉴 막대 숫자 변경(2-5 제외):** 지금 숫자는 쉬었다 돌아온 재구축의 비율이라, 비용의 8분의 1만 말한다. 숫자의 뜻을 묻는 피드백이 오면 올린다.
- **영어 정리 프롬프트 시험:** 영어판은 번역이고 시험하지 않았다. 세션 복제본 두 개에 기본과 영어 A2를 써 보는 데 compact 네 번이 들고, 2-5의 일곱 번이 정가 기준 약 $9 ~ 17이었으므로 약 $5 ~ 10으로 추정한다. 오너의 Claude 사용량을 쓰므로 승인을 받은 뒤에만 한다. 영어 사용자에게서 정리 품질 피드백이 오면 올린다.

**P3, 지지 판정이고 반복 요청이 있을 때:**
- 세션 내용에서 뽑은 체크리스트를 프롬프트에 덧붙이는 방식(2-5 B). 대화 본문을 읽게 되므로 앱이 읽는 범위(DECISIONS 2026-11-18)부터 다시 정해야 한다.
- 메인 세션이 5분 캐시를 쓰고 있다는 사실을 진단 결과로 보여 주기(설계 13장). 터미널·5분 캐시 사용자의 보고가 오면 올린다.
- 큰 세션 기준을 설정으로 바꾸기(2-5 제외). 위 「기본값 재판단」 규칙을 따른다.
- 세션을 눌러 그 세션으로 이동(설계 비목표, 딥 링크 형식 미확인)

**조건이 맞으면 할 것:**
- 공식 `homebrew/cask` 등록(위 판정 기준의 조건)
- `brew audit`(이 기기의 Command Line Tools 업데이트가 먼저다. 관리자 권한이 필요해 오너가 한다)
- 2-5 기기 미확인 두 가지(데스크톱 앱 붙여 넣기, compact 뒤 목록 제외). 이미 오너 할 일에 있다.

**낮음(기록만):**
- 2-5 사소한 항목의 나머지: compact 뒤 경고·알림이 사라지는지 앱 모델 수준의 테스트, 두 목록 갱신 사이의 색인 변경과 코드 주석, compact 확인 쿼리의 중복 조회, `check-strings.py`가 테스트 빌드 폴더도 맞추는 것
- 3-1 LOW: `.notFound`에서 켜기까지 이어지는 모델 수준 테스트
- 3-1 기타: 이 앱 이름으로 남은 손쉬운 사용·Apple Events 권한 검사 로그 확인
- `/compact` 붙여 넣기 길이의 정확한 한계(582자 초과 1,070자 미만 사이)와 IDE에서의 동작

**하지 않음(요청 수만 기록):** 공식 한도 % 표시, 다른 도구(Codex, Cursor) 지원, Windows·Linux. 모두 설계 2장의 비목표다. 요청이 많으면 그 사실을 판정의 "다른 것을 원함"에 반영한다.

### 지키는 선
- 소개 글 게시와 댓글 응대는 오너가 한다. 별, 추천, 댓글을 부탁하지 않는다(Show HN, GeekNews 규칙). 결과 공유 템플릿은 수치 보고를 받는 곳이며 별을 청하지 않는다.
- 관찰 기록에는 집계와 공개 링크만 쓴다. 별을 누른 계정, 댓글 작성자, 댓글 원문, 다른 사용자가 올린 세션 정보는 옮겨 적지 않는다. 피드백은 이슈 번호나 글 링크와 한 줄 요약으로만 남긴다.
- 오너의 Claude 사용량을 쓰는 실험(영어 프롬프트 시험 등)은 비용 추정과 오너 승인이 먼저다.
- 3-2에서는 앱 코드를 바꾸지 않는다. 결함이나 기능은 후속 스테이지로 제안한다. 다만 관찰 중에 "틀림"이나 "환경" 결함이 확인되면, 오너와 정해 바로 고치는 릴리스를 낼 수 있다.

### 흐름과 PR

- 계획 검토(이 PR) → 계획 승인 → (승인 시) 결과 공유 템플릿을 이 PR에 넣음 → 이 PR을 중간 PR로 머지 → 오너가 소개 글 게시(D+0 스냅숏 직후) → D+1 ~ D+30 관찰 → 관찰 기록과 판정을 다음 PR로 → 결과 검토
- 3-2는 코드를 만들지 않지만, 계획 승인 뒤에 관찰과 판정이 있으므로 설계 스테이지로 다루지 않는다. 계획 승인 뒤의 상태는 `IN_PROGRESS`(`구현: 관찰`)이다.
